# Security policy

## Supported versions

The project is pre-release. Security fixes are made on the latest `main` branch until the first stable release establishes a version support table.

## Reporting a vulnerability

Do not open a public issue for a vulnerability, leaked credential, private photograph, project file, or crash dump containing user data.

Use the repository's GitHub **Report a vulnerability** flow (private vulnerability reporting) after the public repository is created. If that flow is unavailable, open a public issue containing no exploit details or private data and ask the maintainers to establish a private channel.

Include only:

- affected version or commit;
- platform and hardware category;
- minimal reproduction without private photographs;
- impact and suggested mitigation;
- whether the issue is already public.

Never attach customer images, RAW/PSD/NPS projects, credentials, access tokens, face embeddings, full file paths, or unredacted logs.

## Response targets

- Critical: acknowledge within 2 business days and prioritize containment;
- High: acknowledge within 3 business days;
- Other: acknowledge within 5 business days.

These are project targets, not contractual service-level agreements.

## Disclosure

Please allow maintainers reasonable time to investigate and publish a fix. The project will credit reporters who request attribution and will not require disclosure of personal identity.
