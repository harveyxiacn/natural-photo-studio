# ADR-0005：显式颜色与像素契约

- 状态：Accepted for M1
- 日期：2026-07-26
- 适用范围：M1 CPU 参考渲染器与 `nps.project/v2`
- 关联：CORE-002、CORE-003、CORE-006、PRO-001、SEC-002

## 背景

M0 用 16 位 P6 PPM 和无 Alpha 的 RGB 整数像素验证了最小可恢复编辑闭环。该路径没有
携带颜色空间标识，也不足以定义图层、蒙版、分块渲染和未来 GPU 后端之间的专业像素
边界。如果继续依赖“调用方知道这是什么颜色”或平台枚举，会产生以下风险：

- 同一组数值在不同节点被解释为不同原色、白点或传递函数；
- 直通透明像素、局部蒙版和曲线在直通/预乘 Alpha 之间产生暗边；
- CPU 金图无法成为 GPU、导出和缓存的独立参考；
- 项目迁移或增加 ACEScg 后，旧文档的工作空间含义发生静默变化；
- PPM 合成测试能力被误写成真实照片编解码或 ICC 色彩管理。

M1 需要先冻结一个窄而完整的边界契约，再扩展格式和设备后端。

## 决定

### CPU 参考像素

M1 CPU 参考缓冲区的逻辑像素固定为按 `R, G, B, A` 顺序排列的四个 IEEE 754
binary32（FP32）分量，并满足：

- RGB 表示场景参考线性光，Alpha 表示覆盖率；
- RGB 使用预乘 Alpha；算子不得凭名称猜测直通 Alpha；
- Alpha 的有效范围为 `[0, 1]`，所有分量必须为有限数；
- 场景线性 RGB 可以小于 `0` 或大于 `1`，中间节点不得隐式裁剪；
- `A = 0` 时规范表示为 `R = G = B = 0`，避免透明像素隐藏不确定数据；
- 颜色算子保持 Alpha，只有明确声明覆盖率语义的算子可以改变 Alpha；
- 缓冲区、节点输入输出、缓存键和持久化记录必须携带颜色空间 ID。缺失、未知或不匹配
  的 ID 是显式错误，不能回退到平台默认值。

“预乘”只规定 Alpha 表示，不表示 `RGB <= A`。宽色域和高动态范围的直通 RGB
经预乘后仍可能产生负值或大于 Alpha 的值。

### 稳定颜色空间 ID

颜色空间使用区分大小写、版本化的稳定字符串 ID，不把 C++ 枚举序号、ICC 文件名或
操作系统句柄写入项目：

| ID | M1 角色 | 含义 |
|---|---|---|
| `nps.color/scene-linear-rec2020-d65/v1` | 默认工作空间 | 采用 BT.2020 原色和 D65 白点，数值为场景线性光；不采用 BT.2020 的非线性视频传递函数 |
| `nps.color/scene-linear-srgb-d65/v1` | 测试辅助空间 | 采用 sRGB 原色和 D65 白点的线性光数值，只服务合成测试和边界验证，不是产品默认空间 |
| `nps.color/scene-linear-acescg-ap1-d60/v1` | 未来保留 | ACEScg 的线性 AP1/ACES 白点契约；M1 不接受该 ID 作为可渲染空间 |

项目必须保存完整字符串 ID。M1 创建的新项目固定保存
`nps.color/scene-linear-rec2020-d65/v1`，以后增加 ACEScg 时也不得改变旧项目的已存
ID。未知 ID 必须以稳定错误拒绝渲染；不得仅因软件升级就重新解释像素。

这里的默认空间是 Natural Photo Studio 的工程决定：
[ITU-R BT.2020](https://www.itu.int/rec/r-rec-bt.2020/en) 提供原色与 D65 等参数依据，
但“scene-linear Rec.2020”是本 ADR 对这些色度参数与线性光编码的明确组合，不能表述
为 BT.2020 本身定义了本项目的场景线性工作流。

[ACES 官方 ACEScg 规范](https://docs.acescentral.com/encodings/acescg/) 规定 ACEScg
使用线性 AP1、ACES 白点以及 16/32 位浮点表示。它证明未来候选具有明确的公开技术
契约，但不表示 M1 已实现 ACEScg 转换或渲染。

### M1 颜色管理边界

M1 只实现上表所列的内建空间边界及当前里程碑实际需要的内建转换。测试辅助 sRGB
空间不得通过隐式标签替换冒充默认工作空间。任意嵌入/外部 ICC profile、ICC v2/v4
解析、显示器 profile、渲染意图、软打样和真实图片 codec 统一推迟到 M2。

[ICC 官方规范页](https://www.color.org/icc_specs2.xalter) 当前列出
ICC.1:2022（Profile version 4.4.0.0），其职责是定义连接颜色编码的 profile 架构和
格式。M1 的稳定内建 ID 不是 ICC profile，也不声称符合完整 ICC 颜色管理链路。

### M0 PPM 的兼容含义

M0 的 16 位 P6 PPM 仅保留为代码生成的合成测试入口和参考导出格式，不是面向用户的
照片导入能力。M1 读取或迁移 M0 合成 PPM 时：

- 把 16 位无符号 RGB 样本归一化为 FP32；
- 补入 `A = 1`；
- 显式赋予 `nps.color/scene-linear-rec2020-d65/v1`；
- 不从 PPM 文件推断 profile，也不把该规则推广到任意外部 PPM。

这个赋值是 M0 无颜色元数据测试资产的版本化兼容解释，不证明文件字节原本带有
BT.2020 元数据。真实 PNG、JPEG、TIFF、RAW 的解码、profile 选择和缺失 profile 策略
必须由 M2 codec/颜色契约另行决定。

## 结果

正面：

- CPU 金图、分块渲染、缓存和未来 GPU 后端共享同一数值边界；
- Alpha、HDR/负值和颜色空间错误可被单元测试精确覆盖；
- 项目重开和版本迁移不会依赖进程内枚举或平台默认 profile；
- 将来可增加 ACEScg 等空间而不静默改变旧项目；
- M1 的窄实现不会被误认为完整 ICC 或真实图片格式支持。

代价：

- 每个像素边界和缓存键都必须传递、校验颜色 ID；
- 预乘/直通转换和零 Alpha 规范化需要专门测试；
- FP32 CPU 参考路径比整数或 FP16 占用更多内存；
- 增加其他工作空间必须提供显式转换、版本和迁移证据。

## 被否决方案

### 用无版本枚举表示颜色空间

实现简单，但枚举序号不适合作为持久化 ABI，也无法安全表达未来参数修订。

### M1 直接接受任意 ICC profile

范围会同时引入 profile 解析、CMM、渲染意图、显示链路、恶意输入和大量兼容矩阵，
无法用 M1 合成像素测试证明正确。该能力进入 M2。

### 继续使用 16 位 RGB PPM 作为内部像素

不能表示 Alpha、负值、场景高光和通用图层组合，无法担当专业渲染参考。

### 默认使用 ACEScg

ACEScg 是有效的未来候选，但 M1 的照片工作流与迁移语料尚未验证其完整代价。先把
颜色 ID 变成持久化契约，使未来选择可显式迁移，而不是提前宣称支持。

## M1 验证要求

本 ADR 的 `Accepted for M1` 表示契约已冻结，不表示实现或测试已经通过。M1 完成前
必须提供：

- FP32 通道顺序、有限值、Alpha 范围、零 Alpha 规范化和不隐式裁剪测试；
- 预乘 Alpha 的曝光、曲线、蒙版组合和透明边缘金图；
- 缺失、未知、错配和未来保留颜色 ID 的拒绝测试；
- M0 合成 PPM 到 FP32 RGBA 的确定性转换与 `v1 → v2` 迁移测试；
- 全图与 ROI/瓦片执行的 CPU 参考差分；
- 项目重开后颜色 ID 逐字节保持的持久化测试。

实际结果只记录在对应提交的 [M1 里程碑说明](../18-milestone-m1.md) 和 CI 证据中。
