# 文档地图与治理

## 1. 文档目的

本目录是 Natural Photo Studio 的产品设计与工程基线文档源。它用于统一产品范围、交互、图像质量、架构、隐私、测试和交付标准，防止“先做一个 AI 按钮，再逐步补专业能力”的方向漂移。当前已经有 M0 可恢复非破坏编辑内核；完整产品设计仍需按本文的治理规则评审。

## 2. 文档状态

| 状态 | 含义 |
|---|---|
| Draft | 方向可讨论，不能作为跨模块接口依据 |
| Proposed | 已给出完整方案，等待产品/技术评审 |
| Accepted | 已评审，可用于实现和验收 |
| Implemented | 已有对应代码和自动化证据；仍须说明适用版本及已知限制 |
| Superseded | 已被新文档或 ADR 取代 |

01–16 号完整产品设计与四份 ADR 当前仍为 `Proposed`。M0 工程基线已经实现，其实际持久化契约以 [`nps.project/v1`](../specs/project-format/nps.project.v1.md) 和 [M0 实现说明](17-milestone-m0.md) 为准。进入对应的完整产品模块开发前，仍需把受影响的产品设计和 ADR 评审为 `Accepted`；M0 的存在不表示未来格式、UI、AI 或安全方案已经冻结。

## 3. 决策优先级

出现冲突时按以下顺序处理：

1. 安全、隐私、数据授权和用户明确选择；
2. 原图完整性、可撤销性和颜色正确性；
3. 产品需求中的验收条件；
4. 已接受的 ADR；
5. 系统与模块设计；
6. 单个功能实现便利性。

不得为了速度绕过前四项。

## 5. 需求可追踪规则

- 产品需求使用 `CORE-*`、`POR-*`、`LAN-*`、`PET-*`、`SKY-*`、`PRE-*`、`REM-*`、`NL-*`、`PRO-*`、`SEC-*` 编号；
- 每个实现任务必须引用至少一个需求编号；
- 每个 P0/P1 需求至少有一个自动化测试或明确的人工视觉验收；
- 命令协议中的操作类型必须能追踪到功能规格；
- 模型版本必须关联模型卡、评测集版本和可回滚构建；
- 需求变更若影响持久化格式、隐私边界或插件兼容性，必须新增 ADR。

## 6. 设计与实现完成定义

一项完整产品能力只有同时具备以下内容，才能从“想法”进入正式模块开发：

- 明确目标用户和任务入口；
- 一键路径与专业手动路径；
- 输入、输出和失败状态；
- 非破坏式表示方法；
- 性能目标与预览策略；
- 自动质量检查；
- 隐私、风险和确认规则；
- 可验证的验收条件；
- 降级或回滚方案。

## 7. 变更记录模板

每份文档顶部在进入实现后应补充：

```text
状态：
负责人：
评审人：
最后更新：
关联需求：
关联 ADR：
```

重大设计调整应在文档底部说明“改变了什么、为什么、迁移影响是什么”，而不是静默改写历史。

已实现里程碑还必须把规范、源码和自动化测试相互链接。若目标设计与当前实现冲突，
必须明确写出“当前实现”与“未来目标”，不得让读者从 Proposed 设计推断代码已经具备
相应能力。
