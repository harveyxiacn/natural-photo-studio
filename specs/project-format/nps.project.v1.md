# `nps.project/v1`：M0 项目目录格式

状态：Implemented（M0）

适用版本：Natural Photo Studio `0.1.x`

实现入口：`include/nps/core/project_store.hpp`、`src/core/project_store.cpp`

## 1. 范围与权威性

本文规定当前 C++ M0 存储内核实际读写的 `nps.project/v1`。它是
[编辑文档与项目格式](../../docs/08-edit-document-model.md) 中长期方案的一个严格子集，
不是完整产品格式的冻结承诺。

M0 仅保存：

- 一份嵌入式、非空的 16 位 P6 PPM 源图对象；
- 累积曝光值；
- 不可变快照、线性撤销/重做游标；
- 命令事务、单项目修订号和幂等结果。

图层、蒙版、RAW、ICC、外链源、预览分支、模型资产、生成补丁、项目迁移和单文件
`.nps` 包均不在本版本内。实现不应根据本文之外的未来设计猜测字段或文件。

## 2. 项目根目录

项目是一个名称以小写 `.npsproj` 结尾的目录。M0 不把它视为普通 ZIP，也不支持直接
打开单文件 `.nps`。

成功创建并至少完成一次打开后的目录如下：

```text
example.npsproj/
├─ project.db
├─ project.lock
├─ objects/
│  ├─ sha256/
│  │  └─ ab/
│  │     └─ cdef...               # 其余 62 个小写十六进制字符
│  └─ .staging/
├─ previews/
├─ recovery/
└─ manifests/
```

运行期间还可能出现：

- `project.db-wal` 与 `project.db-shm`：SQLite WAL 的伴随文件；
- `.nps-creating`：项目发布后、首次成功打开并完成校验前的创建标记；
- 项目父目录中的 `.nps-creating-<随机标识>/`：尚未发布或创建中断的完整暂存目录。

各路径的当前含义：

| 路径 | 是否属于 M0 项目真相 | 含义 |
|---|---:|---|
| `project.db` | 是 | 格式版本、对象索引、快照、历史、事务和幂等记录 |
| `objects/sha256/` | 是 | 以 SHA-256 寻址的不可变字节对象 |
| `objects/.staging/` | 否 | 对象提交前的同项目临时文件；成功提交后通常为空 |
| `previews/` | 否 | 为后续可重建预览预留；M0 不读写内容 |
| `recovery/` | 否 | 为后续恢复资料预留；M0 的恢复事实来自 SQLite/WAL |
| `manifests/` | 否 | 为后续依赖清单预留；M0 不读写内容 |
| `project.lock` | 否 | 跨进程排他租约的承载文件；文件存在本身不表示项目正被占用 |
| `.nps-creating` | 否 | 值必须为 `nps.create/v1\n` 的临时发布标记 |

`project.lock` 在正常关闭后可以继续存在；是否持锁由操作系统文件锁或共享模式决定，
不得通过检查文件是否存在来判断。

## 3. 格式识别

一个 M0 数据库必须同时满足：

- SQLite `application_id = 0x4E505331`；
- SQLite `user_version = 1`；
- `meta.format = "nps.project/v1"`。

任一值缺失或不匹配时，M0 拒绝打开。M1 新增从 v1 到 v2 的显式 side-by-side
迁移器，但普通打开 v1 不会隐式迁移；也没有“尽力猜测”未知主版本的兼容模式。

创建时还会生成 `meta.document_id`。当前形式为 `doc-` 加 32 个小写十六进制字符；
调用方必须把它当作不透明、项目内稳定的标识，而不是用户身份。

## 4. 内容寻址对象

### 4.1 哈希与路径

对象键是对象完整字节的 SHA-256，以 64 个小写十六进制字符表示。路径为：

```text
objects/sha256/<hash[0:2]>/<hash[2:64]>
```

数据库中的 `objects.hash`、路径分片和实际字节摘要必须一致。相同字节得到相同对象
键；对象已存在时，实现重新读取并验证摘要，不静默覆盖。

### 4.2 写入顺序

对象按以下顺序写入：

1. 写到 `objects/.staging/` 内的临时文件；
2. 刷新语言运行时缓冲区，并请求操作系统同步该文件；
3. 将临时文件重命名到最终哈希路径；
4. 重新读取最终文件并校验 SHA-256；
5. 最后在 SQLite 事务中提交引用。

因此，数据库不得引用尚未完成哈希验证的对象。进程在对象发布后、数据库引用提交前
终止时可以留下孤儿对象；完整性检查会计数，但 M0 不自动删除它们。

### 4.3 M0 对象限制

- 源对象必须非空；
- 单对象上限为 8 GiB；
- 创建时登记的媒体类型固定为
  `image/x-portable-pixmap; depth=16`；
- 当前 CLI 和受测调用路径只传入严格的 16 位 P6 PPM 字节，不是原相机文件或外链；
- 存储 API 自身只接收字节并登记固定媒体类型，不会再次解析 PPM；直接调用 API 的
  上层必须先验证输入，否则可能得到媒体类型标记与内容不符的项目；
- 项目包含源图的完整副本，创建项目不会修改或删除调用方原文件。

“内容寻址”提供损坏检测和去重标识，不等于加密、签名、来源证明或恶意内容安全。

## 5. SQLite 连接与持久化配置

所有 M0 表均使用 SQLite `STRICT` 表。每个项目连接启用：

```text
foreign_keys = ON
journal_mode = WAL
synchronous = FULL
temp_store = MEMORY
trusted_schema = OFF
legacy_alter_table = OFF
writable_schema = OFF
ignore_check_constraints = OFF
recursive_triggers = OFF
```

数据库以读写方式打开，并在 SQLite 支持的平台上请求 `SQLITE_OPEN_NOFOLLOW`。WAL 是
项目提交的一部分；不得只复制 `project.db` 而忽略仍存在的 WAL 文件。需要复制或备份
打开中的项目时，应使用 SQLite 支持的备份方式，而不是逐文件复制。

`synchronous = FULL` 与文件同步降低正常本地文件系统上的崩溃丢失风险，但本文不承诺
在所有远程文件系统、故障存储设备、内核错误或突然断电组合下具有相同保证。

## 6. STRICT Schema 的逻辑含义

数据库的物理 Schema 也是版本化项目真相。v1 只接受本节规定的六张表，以及 SQLite
为这些规范约束自动生成的索引；`sqlite_schema` 中不得出现触发器、视图、额外表、
用户创建索引或不同的建表 SQL。把同名列改成更弱约束、增加列，或使用“逻辑上近似”
的 DDL 都不是兼容 v1。`meta` 也必须恰好包含下文六个键，不能借未知键扩展格式。

实现必须在读取可变业务事实和执行任何 `meta` 写入前完成这项精确 Schema 检查。
`trusted_schema = OFF` 等 PRAGMA 是纵深防御，不代替白名单检查；未知触发器即使看似
无害也必须拒绝，不能在打开或迁移过程中执行。

### 6.1 `meta`

| 列 | 约束 | 逻辑含义 |
|---|---|---|
| `key TEXT` | 主键、非空 | 元数据名 |
| `value TEXT` | 非空 | 字符串编码的值；整数值必须可完整解析为有符号 64 位整数 |

实现要求的键：

| 键 | 含义 |
|---|---|
| `format` | 固定为 `nps.project/v1` |
| `document_id` | 当前文档的不透明随机标识 |
| `current_revision` | 最新已提交事务修订号；初始为 `0` |
| `current_snapshot_id` | 当前可见快照 |
| `history_position` | 当前撤销/重做游标 |
| `clean_shutdown` | `1` 表示上次显式关闭完成，`0` 表示项目正打开或上次未干净关闭 |

### 6.2 `objects`

| 列 | 约束 | 逻辑含义 |
|---|---|---|
| `hash TEXT` | 主键、非空 | 64 字符小写 SHA-256 |
| `byte_size INTEGER` | 非空、`> 0` | 对象的准确字节数 |
| `media_type TEXT` | 非空 | 对象媒体类型；M0 创建值固定为 16 位 PPM |

表中每一行都必须有对应的普通文件，且大小和摘要相符。表为空是格式错误。

### 6.3 `snapshots`

| 列 | 约束 | 逻辑含义 |
|---|---|---|
| `id INTEGER` | 主键 | 不透明快照 ID |
| `parent_snapshot_id INTEGER` | 可空、自引用外键 | 创建该编辑快照时的父快照 |
| `created_revision INTEGER` | 非空、唯一 | 快照首次创建的项目修订；初始快照为 `0` |
| `source_hash TEXT` | 非空、外键 | 对 `objects.hash` 的源对象引用 |
| `exposure_ev REAL` | 非空 | 该快照的累积曝光 EV；应用层要求有限数 |

曝光编辑创建新快照。撤销和重做选择已有快照，不复制像素，也不创建新快照。

### 6.4 `history`

| 列 | 约束 | 逻辑含义 |
|---|---|---|
| `position INTEGER` | 主键、`>= 0` | 线性历史中的位置 |
| `snapshot_id INTEGER` | 非空、外键 | 该位置选择的快照 |

有效历史必须从 `0` 开始、没有间断；`meta.history_position` 必须指向其中一行，且该行
的 `snapshot_id` 必须等于 `meta.current_snapshot_id`。在撤销后提交新曝光时，当前游标
之后的 `history` 行会被删除；已存在的快照和事务记录不会因此改写。

### 6.5 `transactions`

| 列 | 约束 | 逻辑含义 |
|---|---|---|
| `revision INTEGER` | 主键、`> 0` | 本次成功命令产生的新修订 |
| `base_revision INTEGER` | 非空、`>= 0` | 命令开始时的修订 |
| `command_id TEXT` | 非空、唯一 | 首次提交该事务的命令 ID |
| `idempotency_key TEXT` | 非空、唯一 | 重试去重键 |
| `request_fingerprint TEXT` | 非空 | 规范化请求载荷；当前保存紧凑 JSON 字符串，并非密码学摘要 |
| `kind TEXT` | 非空 | `adjust.exposure`、`history.undo` 或 `history.redo` |
| `snapshot_id INTEGER` | 非空、外键 | 命令提交后选中的快照 |

每个成功命令——包括撤销和重做——都增加一次 `current_revision`。修订号只增不减。

### 6.6 `idempotency`

| 列 | 约束 | 逻辑含义 |
|---|---|---|
| `idempotency_key TEXT` | 主键、非空 | 查询重试结果的键 |
| `request_fingerprint TEXT` | 非空 | 首次请求的规范化紧凑 JSON；列名中的 fingerprint 不表示哈希 |
| `command_id TEXT` | 非空 | 首次成功提交的命令 ID |
| `base_revision INTEGER` | 非空 | 首次结果的基础修订 |
| `new_revision INTEGER` | 非空 | 首次结果的新修订 |
| `snapshot_id INTEGER` | 非空、外键 | 首次结果的快照 |

命中相同键和相同指纹时，存储层在检查当前修订前返回首次结果，并把结果标记为幂等
重放；传输重试可使用不同 `command_id`。相同键配不同指纹返回
`CMD_IDEMPOTENCY_REUSE`，不得执行新修改。

## 7. 初始状态

新建项目的数据库状态为：

- `current_revision = 0`；
- 快照 `1`：无父节点、`created_revision = 0`、`exposure_ev = 0.0`；
- 历史位置 `0` 指向快照 `1`；
- `transactions` 与 `idempotency` 为空；
- 恰好登记创建输入对应的源对象；
- 数据库暂存阶段的 `clean_shutdown = 1`。

发布后首次成功打开会把 `clean_shutdown` 置为 `0`，表示该项目正在一个写会话中。

## 8. 创建与发布

创建要求目标 `.npsproj` 不存在。Windows 要求其直接父目录不是 reparse point；
POSIX 会先按文件系统语义解析已存在的父目录（包括 macOS 的 `/var → /private/var`
这类系统别名），再拼回尚未解析的最终 `.npsproj` 文件名。这个顺序既保留
`symlink/..` 的真实路径语义，又确保最终项目目录仍能通过 no-follow 状态检查拒绝
符号链接。实现随后在解析所得目标的同一父目录建立随机
`.nps-creating-<随机标识>/`：

1. 写入 `.nps-creating` 标记和目录骨架；
2. 持久化并验证源对象；
3. 在暂存目录中创建并提交数据库；
4. 尝试截断 WAL 并关闭数据库；
5. 将整个暂存目录重命名为最终 `.npsproj`；
6. 按普通打开流程校验项目，再删除内部 `.nps-creating` 标记。

同父目录暂存避免跨文件系统复制窗口，并让“目标不存在”与“目标已发布”可区分。目录
重命名的原子性和持久化边界仍取决于宿主文件系统；M0 没有目录 `fsync` 或跨设备发布
回退，不应把此流程表述为任意存储环境下的断电原子性保证。

若目标已经存在，创建返回 `IO_PROJECT_EXISTS`，不会覆盖它。
在目录发布前发生可捕获异常时，实现会尽力删除本次调用独占创建的暂存目录；清理失败
不会被表述为安全擦除。强制终止或断电不会运行该清理，因此仍可能留下下一节描述的
私人暂存数据。

## 9. 打开、租约与关闭

### 9.1 打开

打开会：

1. 拒绝非目录项目根、链接/reparse 项目根和链接/reparse 数据库；
2. 获取 `project.lock` 的非阻塞跨进程排他租约；
3. 打开 SQLite，先校验 `application_id`、`user_version`，再精确校验
   `sqlite_schema` 和 `meta` 键集合；
4. 读取格式与运行态元数据，并在不写数据库的情况下完成 SQLite、对象、快照、历史、
   事务、幂等及内容哈希的完整检查；
5. 仅在上述所有检查成功后，才在事务中设置 `clean_shutdown = 0`；此前的值只用于
   判断是否从未干净关闭恢复；
6. 保持写会话并向调用方返回已完整验证的项目；
7. 如存在合法 `.nps-creating`，在上述校验成功后删除它。

同一时刻只允许一个 M0 `ProjectStore` 写会话。这个锁只协调遵守该协议的本机进程，
不防止有权限的其他程序直接改写项目文件，也不是分布式锁。

### 9.2 关闭

显式关闭在事务中写入 `clean_shutdown = 1`，然后尽力执行
`wal_checkpoint(TRUNCATE)` 并关闭数据库。检查点失败不会回滚已经提交的项目事实；
WAL 仍由 SQLite 在下次打开时恢复。

析构路径不会向调用方抛出关闭错误，因此需要确认保存状态的应用应显式调用
`ProjectStore::close()` 并处理异常。

## 10. 命令、历史与提交结果

M0 只接收 [严格命令契约](../commands/README.md) 中的三种命令。提交使用
`expectedRevision` 做乐观并发检查；不匹配返回 `REV_CONFLICT`。

- `adjust.exposure`：在当前累计 EV 上加 `[-10, 10]` 范围内的有限增量，创建新快照，
  并在分支编辑时截断前向历史；
- `history.undo`：游标前移到较早快照，但产生新的事务修订；
- `history.redo`：游标后移到较晚快照，但产生新的事务修订。

命令造成的快照选择、事务、幂等记录和三个 `meta` 游标在同一个
`BEGIN IMMEDIATE`/`COMMIT` 事务内更新。若提交调用的最终结果无法确定，调用方会收到
`IO_COMMIT_RESULT_UNKNOWN`；正确恢复方式是用相同 `idempotencyKey` 和相同规范化载荷
重试，而不是生成一个新的键。

## 11. 崩溃与恢复语义

| 终止位置 | 可观察状态 | M0 恢复方式 |
|---|---|---|
| 创建中，源对象已写入但目录尚未发布 | 最终 `.npsproj` 不存在；父目录可能残留 `.nps-creating-*`，其中包含完整源像素 | 可以对原目标重新创建；M0 不自动清理残留暂存目录 |
| 创建数据库完成且目录已发布，但首次打开未完成 | 最终目录存在且带合法 `.nps-creating` | 下一次打开先校验完整项目，再移除标记 |
| 命令 SQLite 事务提交前 | 修订不发布 | SQLite 回滚未提交事务；调用方可重试 |
| 命令 SQLite 事务已提交但进程尚未正常关闭 | 新修订及幂等记录应由 WAL 恢复，`clean_shutdown = 0` | 下一次打开运行完整性检查，并报告本次打开恢复自未干净关闭；用相同幂等键重试可取回原结果 |

当前故障注入测试使用进程立即退出模拟上述边界。这是实现级回归证据，不等价于所有
操作系统、硬件、断电、磁盘满或文件系统损坏场景的证明。

残留 `.nps-creating-*` 目录可能包含私人照片。自动备份、同步、诊断或人工清理工具
必须把它与正式项目同等视为私密数据；在确认标记和精确目标前不得批量删除相似目录。

## 12. 完整性检查

`ProjectStore::open()` 会调用完整性检查；调用方也可显式请求。检查包括：

- `PRAGMA integrity_check` 返回 `ok`；
- `PRAGMA foreign_key_check` 无结果；
- 修订和历史游标为非负整数；
- 当前快照存在，并与当前历史位置一致；
- 历史位置严格连续为 `0..N-1`；
- 事务条数和最大事务修订均与 `current_revision` 一致；
- `objects` 每条记录对应普通文件，大小及 SHA-256 一致；
- 所有快照引用的源对象存在且哈希正确；
- `objects/sha256` 中没有符号链接/reparse point，文件路径严格符合 `2 + 62`
  小写十六进制分片；
- 统计被快照引用的对象数与磁盘上的孤儿对象数。

完整性检查当前只报告孤儿数量，不回收对象；发现其他不变量失败时拒绝继续，而不是
自动修复。它不检查未使用的 `previews/`、`recovery/`、`manifests/` 内容，不验证像素
审美正确性，也不证明文件没有恶意载荷。

POSIX 接受已解析为真实目录的父路径别名，但不会解析最终 `.npsproj` 组件；Windows
保持既有路径解析和 reparse 检查行为。最终项目根、`project.db` 和受保护对象路径会
拒绝已观察到的链接/reparse point，并对 SQLite 与锁文件使用平台可用的 no-follow
打开方式。但是部分路径仍采用“检查后再打开”的普通文件系统流程，存在同权限本地
攻击者竞争改写的剩余风险；M0 项目读取不是安全沙箱边界。

## 13. 隐私与安全边界

M0 命令契约强制：

```json
{
  "network": "deny",
  "cloudInference": "deny"
}
```

当前核心与 CLI 不实现上传或云推理路径。但这不限制操作系统同步软件、备份工具、
杀毒软件或其他有文件权限的进程。

使用方必须了解：

- `.npsproj`、WAL、对象暂存文件及父目录残留的 `.nps-creating-*` 都可能含完整照片；
- 项目未做静态加密，访问控制依赖操作系统权限和用户选择的磁盘加密；
- SHA-256 用于一致性，不用于保密或鉴权；
- 删除文件不承诺 SSD 或文件系统层面的不可恢复擦除；
- 项目根目录、数据库和对象目录的链接防护降低误导路径风险，但不替代低权限解析
  进程、恶意文件模糊测试或针对敌对本地用户的隔离；
- M0 没有遥测上传实现，但上层应用仍必须遵守项目的隐私政策，不能因此推导出未来
  版本“永不联网”。

不得把私有用户照片、真实项目或残留暂存目录提交到公开源码仓库。公开测试使用代码
生成的确定性 PPM，不依赖真实照片。

## 14. 兼容性与演进

`nps.project/v1` 的磁盘含义保持冻结。M1 的显式迁移器把源 v1 只读保留，并在同一
父目录原子发布独立 v2 目标；精确契约见
[`nps.project/v2`](nps.project.v2.md)。任何影响下列内容的后续变化仍需要新规范、
兼容性测试，并按影响决定增加 `user_version` 或新的格式主版本：

- 表或不变量的语义；
- 对象路径、哈希算法或媒体类型；
- 修订、历史或幂等行为；
- 创建标记、锁或崩溃恢复边界；
- 隐私边界或是否允许外链/网络资产。

不应手工修改 `project.db`。v1→v2 迁移只承诺规范中受测的 M0 子集；未知未来版本仍
拒绝写入。
